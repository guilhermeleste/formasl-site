在上一篇文章中，我们把语义计算定义为一种架构：已声明的意义对其实现拥有明确权威。这在抽象层面解决了问题：不同机制可以存储、查询、推理、分析、执行或协调一个应用，而不会因此获得重新定义这个应用意味着什么的权利。剩下需要展示的是，这种分离在 Forma 中如何具体出现。

为此，我们需要首先明确一个此前可以暂时留在背景中的区别。FormaSL 并不是 Forma 的同义词。FormaSL 是可计算语义规范语言。Forma 则是技术架构与生态系统，它围绕这样一种可能性组织起来：声明语义结构化的世界，并通过不同机制实现这些世界，同时不把对契约的权威委托给这些实现机制。

这个区别很重要，因为走到本系列结尾时，人们很自然会设想：表示、查询、推理、存储、执行、创作、运行和基础设施最终应该汇聚到一个能够完成一切工作的巨大运行环境中。Forma 架构采取相反方向。它分离责任，是因为意义与实现之间存在的区别，在我们从语言进入系统的具体组件之后仍然必须保持可见。

基本地图可以表示如下：

```text
语义层
世界 + .fsl 契约 + 操作
              │
              │ 语义义务
              ▼
实现层
.fsp 实现配置
              │
              │ 选择并绑定能力
              ▼
运行层
存储 · 查询 · 推理 · 分析
执行 · 观察 · 其他能力
```

这张图并不是规定所有应用都必须依次经过的强制流程，而是一张责任地图。有些应用只会使用其中一部分能力；另一些会组合不同机制，或以不同方式分布计算。始终不变的是三者之间的边界：系统声明自己意味着什么；实现为了满足这个契约而选择什么；以及当被选择的机制真正进入运行后实际发生什么。

FormaSL 位于语义层。它当前的逻辑表示是一个基于角色的类型化关联元图：关系可以保持自身身份，参与者占据语义上定义的角色，而结构本身又可以参与高阶关系。这项选择属于逻辑模型。它并不决定每个关系必须以什么形式出现在内存、磁盘或实现所使用的索引中。

`.fsl` 是已声明意义的权威来源。在这一层，类型、关系、Claim、规则、政策、语境和操作共同构成被表示世界的可计算契约。这种权威仍然严格限定在契约内部：一个 Claim 不会因为被声明就变成真实；一种形式化不会变成它所表示的外部规范；一项计算授权也不会自动在现实世界中产生效果。

在支撑本系列的仓库切片中，这套架构已经拥有具体的语言表面。存在用于查询、分析、推理、转换、验证、准入、授权、决策、修订、场景、执行请求、观察、源演化和纳入的操作。在同一个切片中，Claim 生命周期保留了身份、内容、发出者、依据与语义发生等要素。因此，本系列在概念层面逐步建立的一部分区别，已经进入语言和经过验证的实现结构之中。

当前文档认为 FormaSL 在当前语义边界下已经作为语言完成。这个限定仍然非常重要：它并不意味着所有可以想象的领域都已经被建模，不意味着未来不会继续演化，也不意味着生态系统的其他部分已经完成。它意味着，在这一阶段所建立的语义边界内，项目认为语言核心要求的基本区别集合已经闭合。

这种闭合让其他决策可以留在语言之外。某个应用可能需要新的数据库、算法、统计模型或分布式机制，而这些需求并不要求语言因此增加新的原语。下一层存在的目的，正是为了把这些需要与语言核心分开。

`.fsp` 属于实现层。它的功能不是建立第二套语义，而是描述契约所要求的能力将如何得到满足。一个应用可能需要存储自己的世界、查询关系、执行推理、进行分析、使用机器学习、协调工作或请求外部行动。实现配置把这些需要绑定到负责满足它们的具体机制。

因此，技术策略可以根据问题变化。在某些情况下，生态系统自身可以提供某项能力；在另一些情况下，可以集成一种专用实现；还有一些情况下，可以把实现委托给外部基础设施。在当前生态系统设计中，这三种可能性可以理解为“自有、集成或委托”。它们不是新的语义类别，而只是满足既有契约的不同方式。

当这些选择变成具体机制时，就进入运行层。存储负责持久化表示。查询机制寻找结构。推理系统推导结果。模型可以完成分析。执行器尝试产生行动。观察可以把外部结果的信息返回系统。每个组件都有自己的技术职能；这种职能并不会自动赋予它对流经自身的意义拥有权威。

Forma 生态系统的各个组件，可以在这套分解中被定位。

FormaDB 属于数据领域。在当前生态系统设计中，它被设想为 Forma 世界的原生数据系统。“原生”意味着它可以专门围绕这些世界的属性与需要进行设计；并不意味着语言在本体意义上依赖 FormaDB。如果另一种存储实现能够满足契约的相关义务，一个 FormaSL 应用也可以使用其他存储系统。

逻辑元图同样不意味着 FormaDB 必须在物理上存储一个图。它的实现可以根据运行要求选择合适的结构、索引和表示，只要语义上要求的属性继续得到保留或可以重建。此前建立的区别即使对生态系统自己设计的数据系统仍然有效：元图语义并不意味着物理图存储。

当前产品决策还为 FormaDB 记录了一种开放或社区化的参考方向，以及未来提供托管服务的可能性。这属于生态系统设计，而不是 FormaSL 的规范语义，因此不能被理解为对许可证、商业可用性或最终实现状态的声明。

Forma Platform 承担另一类责任。它被设想为用于运行 Forma 世界与计算，并协调其实现所需能力的集成产品。如果把它简化成一个基础设施控制中心，就会丢失它真正要操作的对象：那些世界、操作和实现都具有显式语义结构的应用。

这种运行可能涉及存储、推理、分析、执行、资源与外部集成。Platform 不需要在内部自有全部这些能力。它可以协调 Forma 自身提供的机制和外部专用机制，只要这些机制之间的关系以及它们与契约之间的关系保持显式。不过，协调计算并不会让 Platform 成为它所协调意义的来源。这个权威仍然位于 `.fsl`。

Forma Studio 回答的是另一种需要：让人能够实际使用并处理这套系统。它被设想为用于 Forma 世界与契约的创作、建模、检查和调试环境。以声明方式存在于 `.fsl` 中的结构，可以在 Studio 中获得更适合编辑和调查的可视化与交互形式，而无需让界面成为这些结构意义的所有者。

Studio 可以维护界面状态、产生辅助表示，并提供对创作有帮助的抽象。但是，任何对契约具有实质意义的内容都不应依赖只隐藏在工具内部的信息。界面可以帮助人们产生和理解这个世界，却不能因此变成第二个语义来源。

在当前产品设计中，Studio 采用本地优先方向，核心本地工作流被设想为无需依赖账户即可运行。这是一项产品决策，而不是语言的语义要求，但它与架构保持一致：契约是否可以被理解，不应取决于它是否只存在于某个专有远程服务之中。

Forma Cloud 则属于托管实现领域。它被设想为生态系统自身提供的一种可选方案，面向希望在托管基础设施上运行 Forma 应用的用户。它可以集中提供资源、集成与运行便利，避免每次部署都分别重建这些能力。

Cloud 的可选性在架构上非常重要。Forma Cloud 不是使用 FormaSL 的必要条件，应用被托管以后，语义权威也不会迁移到 Cloud。如果正确解释一个 `.fsl` 必须依赖隐藏在云中的语义，契约就不再真正具有权威性。如果只有托管基础设施才能合法地实现一个应用，那么所谓“实现自由”也只剩下名义。Cloud 可以成为与生态系统深度集成的实现，同时仍然只是一个实现。

这些责任可以归纳如下：

| 组件 | 主要责任 | 与语义权威的关系 | 与 FormaSL 的关系 |
|---|---|---|---|
| FormaSL / `.fsl` | 声明世界、契约与语义操作 | 已声明意义的权威来源 | 语义核心 |
| `.fsp` | 描述实现配置 | 满足契约；不重新定义契约 | 实现层 |
| FormaDB | 原生实现数据领域 | 不重新定义契约 | 原生存储，但非强制 |
| Forma Platform | 运行并协调世界、计算与实现 | 不重新定义契约 | 集成产品，不是语言要求 |
| Forma Studio | 创作、建模、检查与调试 | 不重新定义契约 | 可选工作环境 |
| Forma Cloud | 提供托管实现 | 不重新定义契约 | 可选实现 |

这张表同样不表示一个权威堆栈。Cloud 在语义上并不高于 Platform；Platform 也不高于 FormaDB；Studio 不会因为被用来生成契约，就成为意义来源。这些组件之间存在依赖、集成与运行关系，但对已声明意义的权威并不会仅仅因为组件被组合起来就向上传播。

这个区别解释了为什么生态系统被设想为可组合的，而不是一个不可分割的软件包。FormaSL 不依赖 Cloud。FormaDB 不是 Forma 应用存在的本体条件。Studio 可以参与创作，却不是执行所必需。Platform 可以运行内部能力与外部能力。Cloud 可以提供托管实现，而不会垄断契约可能的执行方式。

可组合也不意味着任意组件集合无需集成工作就能自动运行。外部机制仍然必须满足技术契约、运行属性和语义义务。有些组合可能要求大量工程工作；另一些则可能因为更深的集成而天然更有优势。架构并不承诺所有实现之间都具有运行等价性。它允许我们把基础设施选择与应用意义的变化区分开。

语义连续性贯穿整张地图。它并不专属于编译器、存储、Platform 或任何单一产品。当 `.fsl` 被细化，当实现配置被解析，当结构被物化，当分析被执行，或者当来自外部世界的观察返回时，每次跨越都可能保留、转换或擦除后续解释仍然需要的信息。

如果某个结果仍然依赖一个场景，这种依赖在结果被存储时不能消失。如果 Claim 的发出者对解释仍然具有实质意义，一次投影就不能悄无声息地把它变成没有归属的命题。如果某个决策产生了执行请求，一条运行响应不能抹去“作出决策、尝试执行、产生效果、观察效果”之间的区别。实现自由始终从属于这些义务。

这并不允许我们声称当前整个生态系统已经为任何可能的转换提供完整的端到端可追溯性。当特定谱系、依赖或区别具有实质必要性时，架构会建立保留与重建义务；当前实现切片则为特定属性提供证据。如果要声称覆盖全部情形，就需要与该主张相对应的证明。

因此，我们最后还需要一个区别，才能正确阅读这张地图。关于 Forma 的所有陈述并不拥有相同地位。`.fsl` 的权威、契约与实现之间的分离、逻辑元图以及语义连续性的义务，属于当前规范架构。语言表面与 Claim 生命周期的特定行为，则已经在本系列所使用的仓库切片中得到验证。FormaDB、Platform、Studio 和 Cloud 则包含当前关于生态系统与产品组织方式的决策。这些决策可以表明 Forma 的技术方向，但不能自动被转换成关于商业可用性、成熟度、许可证、价格或服务等级的声明。

把这些不同层次分开，会让架构更加精确，而不是更不确定。规范性、实现与产品可以以不同速度演化，而无需让某个暂时的代码状态重新定义契约，也无需把一项产品决策描述成已经得到证明的能力。

现在，我们可以把 Forma 作为一个完整系统来观察，而不需要把它还原成其中任何一个部分。FormaSL 声明世界和操作；实现配置把这些契约连接到所需能力；数据系统可以物化它们的状态；专用机制可以查询、推理、分析和执行；Platform 可以协调这些能力；Studio 可以让人对它们进行操作和检查；Cloud 可以提供托管实现；外部机制在满足相应义务时也可以参与其中。没有任何一个组件需要变成通用机器，也不需要独自取得它所帮助计算之世界的语义所有权。

到这里，架构重新回到了开启整个系列的问题。

具体企业先于它的系统而存在。为了让企业变得可计算，我们把它的各种规定分解到了账本、数据库、商务系统、身份机制、规划工具、模型、界面以及大量其他专业化工具之中。这种分解并不是错误：正是它让组织的不同方面在运行上变得可处理。问题出现在每个切面也开始隐含地携带自己的那一部分意义之后，于是整体性必须再通过标识符、集成、约定以及散布在不同系统中的知识重新构建。

在系列结束时，专业化仍然存在。我们仍然有语言、存储、推理、分析、执行、界面、平台与基础设施。我们并没有尝试用一种单一技术取代所有这些东西。

真正改变的是整体性所在的位置：多个切面与多种实现仍然可以属于同一个世界，因为把它们联系起来的意义并没有被委托给其中任何一个组件。
